# Bản ghi: `hello` có DB (JdbcClient, Flyway, PgBouncer, profile `migrate`, chặn sửa migration)

Ticket [G0-26](../.scratch/g0-platform/issues/26-hello-jdbc-flyway.md). Bằng chứng theo bảng "Bằng chứng cần có" của [db-migration.md](../standards/db-migration.md) và mục "AOT cache" của [container-image.md](../standards/container-image.md). Đo ngày **2026-11-24** và **2026-11-25** trên Mac M1 (Docker Desktop, arm64) và GitHub Actions (`ubuntu-24.04`, amd64).

## Bối cảnh

Spring Boot 4.1.2, Java 25, Flyway 12.4.0, pgjdbc do Boot quản lý, Testcontainers 2.0.5. Container trong test giống `pg-main` trên lab: `postgres:18.7` (lab `gitops/infra/pg-main/cluster.yaml`), PgBouncer image CNPG `1.25.2-202609221033-trixie` ghim digest (lab `gitops/infra/pg-main/pooler.yaml`), `pool_mode = transaction`. Bốn role như CR `DatabaseRole` của lab: `hello_owner`, `hello_lookup`, `hello_migrator`, `hello_app`. Runtime đăng nhập `hello_app` qua PgBouncer; Flyway đăng nhập `hello_migrator` nối thẳng PostgreSQL.

## Giả thuyết

1. Prepared statement có tên của pgjdbc (sau `prepareThreshold=5` lần) chạy được qua PgBouncer `transaction` vì `max_prepared_statements` mặc định 200 (docs 1.25.2).
2. `init-sqls` (`SET ROLE hello_owner`) chạy trước khi Flyway tạo `flyway_schema_history`, nên mọi bảng thuộc `hello_owner` (điểm **chưa xác minh** của db-migration.md).
3. Migration đầu chạy được từ DB trống trên cả PostgreSQL 17 và 18.
4. Profile `migrate` thoát mã 0 khi thành công, khác 0 khi lỗi, mà không cần `FlywayMigrationStrategy` hay `System.exit` (điểm **chưa xác minh** thứ hai), và không mở cổng nào.
5. Job `migration-guard` đỏ khi PR sửa migration đã có, xanh khi PR chỉ thêm migration mới.

## Cách đo

- Test JUnit trong `services/hello` (`./gradlew test`), mỗi test chạy trên container mới của Testcontainers.
- Với mỗi lớp bảo vệ, làm một **đối chứng âm**: tạm gỡ lớp đó, xác nhận test đỏ, rồi trả lại.
- Profile `migrate`: `java -jar build/libs/hello-0.0.1-SNAPSHOT.jar --spring.profiles.active=migrate --spring.flyway.url=… --spring.flyway.user=hello_migrator --spring.flyway.password=…` vào một container `postgres:18.7` riêng có script bốn role; `echo $?`. Cổng đang nghe: `lsof -a -p <pid> -iTCP -sTCP:LISTEN` mỗi 0,1 s suốt đời process. Đối chứng: cùng lệnh, thêm `--spring.main.web-application-type=servlet`.
- Image: `docker build` ở máy (arm64), chạy với `JAVA_TOOL_OPTIONS=-XX:AOTMode=on` (không nạp được cache thì JVM từ chối khởi động) ở profile `migrate` và runtime, so dòng `Started HelloApplication in N seconds` với `-XX:AOTMode=off`.
- `migration-guard`: hai PR nháp có base là nhánh `g0-26` trên `commerce-hub-hello`, đọc kết quả bằng `gh pr checks` và annotation của check run.

## Kết luận

- **Giả thuyết 1–5 đạt.** Hai điểm chưa xác minh của db-migration.md (thứ tự `init-sqls`, cách thoát của profile `migrate`) đã có kết quả và được ghi vào chuẩn.
- **Test không bắt được việc sửa migration cũ**: ở PR #4, `ci / check` vẫn xanh vì test luôn migrate trên DB trống. Lớp `migration-guard` là cần thiết, không thừa.
- **Thêm DB làm hỏng training run AOT** mà test không thấy, vì test không build image. Chỉ CI của PR mới lộ. Service G1 có DB dùng lại cách URL `.invalid`.
- **Thời gian migration** dao động 52–160 ms tùy JVM nóng hay lạnh; số này chỉ có ý nghĩa như mốc, không dùng để so.
- **Còn mở:** Job PreSync và kết nối tới `pg-main-rw` trên lab (ticket 27); hai nhánh thêm migration merge ngược thứ tự timestamp chỉ lộ ở `validate` của Job, chưa có lớp chặn ở CI.
