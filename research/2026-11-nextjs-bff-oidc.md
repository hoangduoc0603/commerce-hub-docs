# Next.js BFF làm OIDC client cho Keycloak (proxy, SSE, thư viện auth, verify email, back-channel logout)

Tra cứu ngày 13/11/2026. Bối cảnh: app Next.js (App Router, TypeScript, `output: 'standalone'`, Node runtime) đóng vai BFF. Phía server là confidential OIDC client của Keycloak 26.8.2 (Authorization Code + PKCE S256; Revoke Refresh Token ON, tức refresh token chỉ dùng được một lần; access token sống 5 phút; backchannel logout URL trỏ về BFF). Browser chỉ giữ một session cookie HttpOnly. BFF chuyển tiếp lời gọi của browser sang Spring Cloud Gateway nội bộ và gắn thêm `Authorization: Bearer`. Phase 2 cần stream Server-Sent Events qua BFF.

Cách tra: tài liệu Next.js đọc từ mã nguồn docs ở tag `v16.4.6` (`github.com/vercel/next.js/tree/v16.4.6/docs`). Keycloak đọc docs và mã Java ở tag `26.8.2`. Auth.js, Better Auth, openid-client đọc từ tarball npm của bản mới nhất, và từ docs trong repo ở tag hoặc `main`. Phiên bản lấy từ npm registry (`registry.npmjs.org/<pkg>`) và GitHub Releases API.

Nhãn: **[CT]** tài liệu hoặc mã nguồn chính thức · **[CXM]** chưa xác minh · **[SL]** suy luận của người viết, chưa có nguồn nói thẳng.

## Tóm tắt

- **Next.js** bản stable là **16.4.6** (09/11/2026). Từ v16, `middleware.ts` bị deprecated và đổi tên thành **`proxy.ts`**. `proxy` luôn chạy Node.js runtime, không cấu hình được. Muốn Edge thì phải giữ `middleware.ts`.
- **SSE qua Route Handler:** trả `new Response(upstream.body)` là stream được. Next.js ghi từng chunk ra `res` rồi gọi `res.flush()`, nên gzip của `compress` không gom chunk lại. Lúc client ngắt kết nối, `close` của response kích hoạt `request.signal`, và ta truyền signal này vào `fetch` upstream. Có hai điểm phải đo bằng thí nghiệm: hành vi abort trên bản standalone cụ thể đang dùng **[CXM]**, và nginx hay ingress đứng trước phải tắt buffering.
- **Auth.js / NextAuth v5:** đã "là một phần của Better Auth" (22/09/2025). Nhóm chỉ còn vá bảo mật và lỗi khẩn. v5 vẫn là `5.0.0-beta.32`. Auth.js có database session, nhưng **không có back-channel logout**, và chính docs thừa nhận có race khi refresh token đồng thời.
- **Better Auth 1.7.22:** plugin `generic-oauth` có helper `keycloak`, discovery, PKCE, tự refresh token, RP-Initiated Logout, session lưu trong Postgres. **Không có back-channel logout phía RP.** Code refresh không có khóa, nên vẫn race khi refresh token single-use.
- **openid-client 6.8.9** (v6 là major hiện hành, còn bảo trì đủ). Thư viện **không có helper validate `logout_token`**: phải dùng `jose` (`jwtVerify` + `createRemoteJWKSet`) và tự kiểm theo spec mục 2.6. Chạy tốt trên Node runtime (cần Node ≥ 20).
- **Keycloak "Verify email" ON thì chặn login:** required action `VERIFY_EMAIL` được gắn cho user chưa verify, và user phải làm xong mới được cấp token. Không có option nào làm nó thành không chặn. Muốn không chặn thì để realm Verify email **OFF** và cho app chủ động gọi AIA `kc_action=VERIFY_EMAIL`. Ở refresh grant, Keycloak dựng lại access token và ID token qua protocol mapper từ user model hiện tại, nên `email_verified` được tính lại.
- **`sid`:** luôn có trong access token và ID token (bằng id của user session). Trong `logout_token`, `sid` chỉ có khi bật *Backchannel logout session required*. Back-channel logout **được gửi** khi đổi hoặc reset mật khẩu có tích "Sign out from other devices", khi admin "Sign out" một user, và khi xóa một session. **Không gửi** khi admin bấm "Sign out all active sessions" của cả realm.

Bảng version history: v15.5.0 Middleware dùng được Node runtime ở mức stable; v16.0.0 đổi tên thành Proxy, mặc định Node.js. Nguồn: `proxy.mdx` mục *Runtime* và *Version history*, tra 2026-11-13 [CT].

### 1.3 Stream SSE qua Route Handler

**Trả stream:** docs Route Handler có mục *Streaming*, minh họa bằng `return new Response(stream)` với `ReadableStream` [CT]. Từ v15.0.0-RC, `GET` handler mặc định là dynamic ("Route Handlers are not cached by default"), nên SSE không cần `force-dynamic` [CT]. Nguồn: [`route.mdx`@v16.4.6](https://github.com/vercel/next.js/blob/v16.4.6/docs/01-app/03-api-reference/03-file-conventions/route.mdx), [`15-route-handlers.mdx`@v16.4.6](https://github.com/vercel/next.js/blob/v16.4.6/docs/01-app/01-getting-started/15-route-handlers.mdx), tra 2026-11-13.

**Không buffer ở tầng Next.js:** `createWriterFromResponse` trong `pipe-readable.ts` gọi `res.flushHeaders()` ở chunk đầu tiên. Với mỗi chunk, nó gọi `res.write(chunk)` rồi gọi `res.flush()` nếu có. `res.flush()` là hàm do middleware `compression` thêm vào để "flush the partially-compressed response to the client". Code cũng chờ `drain` khi gặp backpressure. Nguồn: [`packages/next/src/server/pipe-readable.ts`@v16.4.6](https://github.com/vercel/next.js/blob/v16.4.6/packages/next/src/server/pipe-readable.ts), tra 2026-11-13 [CT]. Vậy trả thẳng `new Response(upstream.body)` thì mỗi chunk upstream đi ra browser ngay [SL, suy từ code].

**Ngắt kết nối từ client:** `createAbortController(response)` abort khi `close` của `ServerResponse` xảy ra trước `finish`. `signalFromNodeResponse` dùng hàm này, và `NextRequestAdapter.fromNodeNextRequest(request, signal)` gắn signal đó vào `NextRequest`. Nguồn: [`server/web/spec-extension/adapters/next-request.ts`@v16.4.6](https://github.com/vercel/next.js/blob/v16.4.6/packages/next/src/server/web/spec-extension/adapters/next-request.ts), tra 2026-11-13 [CT]. Mẫu dùng là `fetch(upstreamUrl, { signal: request.signal, headers })`. Client đóng tab thì signal abort, kết nối tới Gateway đóng theo [SL].

- Issue [vercel/next.js#101049](https://github.com/vercel/next.js/issues/101049) (đang mở) dùng Route Handler làm nhóm đối chứng trên 16.3.3, 16.4.2 và 16.5.0-canary.36 bản production build: `request.signal` abort, kết nối backend đóng trong 1,8 s. Lỗi của issue nằm ở RSC `cacheSignal()`, không phải ở Route Handler. Đây là báo cáo của người dùng, chưa có maintainer xác nhận, tra 2026-11-13 **[CXM]**.
- Discussion cũ [#48682](https://github.com/vercel/next.js/discussions/48682) có báo cáo trên Next 14.2.3 rằng `abort` không bắn khi browser hủy request. Với 16.4.6 standalone, phải tự đo **[CXM]**.

**`compress` và SSE:**
- `next start` và server tự viết (standalone `server.js` cũng dùng chung server này [SL]) mặc định nén gzip. Tắt bằng `compress: false` nếu nén đã làm ở reverse proxy. Nguồn: [`compress.mdx`@v16.4.6](https://github.com/vercel/next.js/blob/v16.4.6/docs/01-app/03-api-reference/05-config/01-next-config-js/compress.mdx), tra 2026-11-13 [CT].
- Bản `compression` vendored bỏ qua nén khi response có `Cache-Control: no-transform`, hoặc khi đã có `Content-Encoding` khác `identity`. Nguồn: [`packages/next/src/compiled/compression/index.js`@v16.4.6](https://github.com/vercel/next.js/blob/v16.4.6/packages/next/src/compiled/compression/index.js), tra 2026-11-13 [CT]. Với SSE, nên đặt `Cache-Control: no-cache, no-transform` [SL].
- Có file `server/lib/release-compression-stream.ts`. Comment trong đó ghi: middleware `compression` để zlib stream mở khi client ngắt kết nối, và mỗi stream giữ khoảng 256 KiB native mãi mãi. Hàm `releaseCompressionStream` hủy stream đó. Nguồn: [`release-compression-stream.ts`@v16.4.6](https://github.com/vercel/next.js/blob/v16.4.6/packages/next/src/server/lib/release-compression-stream.ts), tra 2026-11-13 [CT]. Hàm này có được gọi trên đường đi của Route Handler hay không thì chưa kiểm **[CXM]**. Với kết nối SSE dài và hay bị ngắt, `no-transform` (hoặc `compress: false`) né được rủi ro rò bộ nhớ [SL].

**Hạ tầng phía trước:** docs self-hosting yêu cầu tắt buffering ở nginx hoặc proxy tương tự, ví dụ header `X-Accel-Buffering: no`. Load balancer và reverse proxy phải chuyển chunked response đi mà không buffer. Nguồn: [`docs/01-app/02-guides/self-hosting.mdx` mục Streaming and Suspense](https://github.com/vercel/next.js/blob/v16.4.6/docs/01-app/02-guides/self-hosting.mdx), tra 2026-11-13 [CT].

Checklist SSE cho BFF [SL]: `runtime` mặc định (nodejs); response header `Content-Type: text/event-stream`, `Cache-Control: no-cache, no-transform`, `X-Accel-Buffering: no`; truyền `request.signal` vào `fetch` upstream; heartbeat comment `:` định kỳ để vượt idle timeout của ingress. Thí nghiệm cần chạy: đóng client, rồi xem kết nối BFF→Gateway có đóng không.

## 4. openid-client và jose

- **Phiên bản:** `openid-client` `latest` = **6.8.9** (02/11/2026); bảng Supported Versions chỉ có v6.x, nhận cả vá bảo mật, sửa lỗi và tính năng mới. Phụ thuộc `oauth4webapi ^3.8.8` và `jose ^6.2.15`. `jose` `latest` = 6.2.17 (09/11/2026). Nguồn: [npm `openid-client`](https://registry.npmjs.org/openid-client), [npm `jose`](https://registry.npmjs.org/jose), README và `package.json` trong tarball `openid-client@6.8.9`, tra 2026-11-13 [CT].
- **Tính năng:** discovery, Authorization Code (OIDC, OAuth 2.1, FAPI), Refresh Token, Device, CIBA, Client Credentials, DPoP, introspection/revocation, PAR, JAR/JARM, DCR. Đã có chứng nhận OpenID cho các profile Basic RP, FAPI 1.0 và FAPI 2.0. Nguồn: [README](https://github.com/panva/openid-client/blob/v6.x/README.md), tra 2026-11-13 [CT].
- **Back-channel logout:** README không liệt kê. Trong `build/index.d.ts`, "backchannel" chỉ xuất hiện ở CIBA (`initiateBackchannelAuthentication`); không có API nào verify `logout_token`. Nguồn: tarball `openid-client@6.8.9`, tra 2026-11-13 [CT]. Vậy phải tự verify bằng `jose`: `createRemoteJWKSet(jwks_uri)` và `jwtVerify(token, JWKS, { issuer, audience: clientId, typ: 'logout+jwt', algorithms: [...] })`. Sau đó tự kiểm các claim theo spec [SL, cách dùng API jose].
- **Các bước validate theo [OpenID Connect Back-Channel Logout 1.0](https://openid.net/specs/openid-connect-backchannel-1_0.html) mục 2.4–2.8**, tra 2026-11-13 [CT]:
  1. Kiểm chữ ký như ID token; `alg` không được là `none`.
  2. Kiểm `iss`, `aud`, `iat`, `exp` (tất cả REQUIRED, cùng với `jti` và `events`).
  3. Phải có `sub`, `sid` hoặc cả hai.
  4. `events` phải có member `http://schemas.openid.net/event/backchannel-logout`.
  5. **Không** được có `nonce`.
  6. Tùy chọn: chống replay bằng `jti`; đối chiếu `iss`, `sub`, `sid` với ID token.
  7. Header `typ` RECOMMENDED là `logout+jwt`.
  8. Trả 200 (OP nên chấp nhận cả 204) khi thành công, 400 khi lỗi; nên kèm `Cache-Control: no-store`.
- **Runtime:** hỗ trợ mọi runtime có Web API cần thiết (WebCrypto, Fetch): Node.js (baseline v20), Deno, Cloudflare Workers… Gói là ESM; `require` được trên Node có `require(esm)` (^20.19 / ^22.12 / ≥23). Nguồn: README mục Supported Runtimes, tra 2026-11-13 [CT]. Route Handler của Next.js chạy Node nên dùng được [SL].

## 5. Keycloak 26.8: Verify email

Phiên bản: 26.8.2 phát hành 05/11/2026 (26.8.0 ngày 01/10/2026). Nguồn: GitHub Releases API `keycloak/keycloak`, tra 2026-11-13 [CT].

- **Verify email ON thì chặn login.** Trong `VerifyEmail.evaluateTriggers`, nếu `realm.isVerifyEmail()` và `!user.isEmailVerified()` (và user có email, chưa có `UPDATE_EMAIL`), Keycloak gắn `RequiredAction.VERIFY_EMAIL` cho user. Nguồn: [`services/.../requiredactions/VerifyEmail.java`@26.8.2](https://github.com/keycloak/keycloak/blob/26.8.2/services/src/main/java/org/keycloak/authentication/requiredactions/VerifyEmail.java), tra 2026-11-13 [CT]. Docs mô tả *Verify Email*: user phải bấm link trong email, "Once this workflow is successfully completed, the user will be allowed to log in". Nguồn: [`server_admin/topics/users/con-required-actions.adoc`@26.8.2](https://github.com/keycloak/keycloak/blob/26.8.2/docs/documentation/server_admin/topics/users/con-required-actions.adoc), tra 2026-11-13 [CT]. Vậy login không tới được bước cấp code/token cho tới khi verify xong; không có trường hợp "đăng nhập được với `email_verified=false`" khi option này ON [SL từ docs và code].
- **Không có option làm verify thành không chặn.** Config metadata của required action này chỉ gồm `max_auth_age` và cooldown gửi email (`EmailCooldownManager`). Release notes 26.7.0, 26.8.0 và upgrading notes 26.8.0 không thêm option như vậy. Nguồn: `VerifyEmail.java` (`getConfigMetadata`), [`release_notes/topics/26_8_0.adoc`](https://github.com/keycloak/keycloak/blob/26.8.2/docs/documentation/release_notes/topics/26_8_0.adoc), [`upgrading/topics/changes/changes-26_8_0.adoc`](https://github.com/keycloak/keycloak/blob/26.8.2/docs/documentation/upgrading/topics/changes/changes-26_8_0.adoc), tra 2026-11-13 [CT].
- **Cách không chặn: realm Verify email OFF, app gọi AIA.** `VerifyEmail.initiatedActionSupport()` trả `SUPPORTED`, nên app có thể redirect tới authorization endpoint kèm `kc_action=VERIFY_EMAIL` lúc nào cần (ví dụ khi bật tính năng yêu cầu email đã verify). User hủy thì redirect về kèm `kc_action_status=cancelled`. Docs cảnh báo: dùng `kc_action` không bảo đảm user đã làm action; app phải tự kiểm lại qua claim (ở đây là `email_verified`). `kc_action` là cơ chế riêng của Keycloak, không thuộc OIDC. Nguồn: `VerifyEmail.java`, [`server_admin/topics/users/con-aia.adoc`@26.8.2](https://github.com/keycloak/keycloak/blob/26.8.2/docs/documentation/server_admin/topics/users/con-aia.adoc), tra 2026-11-13 [CT].
- **Thay đổi 26.8.0 liên quan:** email chỉ được đánh dấu verified khi user hoàn tất verify email. Trước đây vài flow khác cũng đánh dấu, như account linking với IdP theo email, hay email admin action không có *Verify Email*. *Trust Email* của IdP và LDAP không bị ảnh hưởng. Nguồn: `changes-26_8_0.adoc` mục "Email is no longer marked as verified by other flows", tra 2026-11-13 [CT].
- **Refresh grant tính lại claim từ user hiện tại.** `AbstractRefreshTokenProvider` lấy `user` từ `validateToken` (`userSession.getUser()`, kèm kiểm user enabled, `notBefore`, consent) rồi gọi `tokenManager.createClientAccessToken(...)`. Hàm này chạy `transformAccessToken` qua các protocol mapper; ID token cũng được dựng lại bằng `generateIDToken()`. Nguồn: [`protocol/oidc/refresh/AbstractRefreshTokenProvider.java`@26.8.2](https://github.com/keycloak/keycloak/blob/26.8.2/services/src/main/java/org/keycloak/protocol/oidc/refresh/AbstractRefreshTokenProvider.java), [`protocol/oidc/TokenManager.java`@26.8.2](https://github.com/keycloak/keycloak/blob/26.8.2/services/src/main/java/org/keycloak/protocol/oidc/TokenManager.java), tra 2026-11-13 [CT]. Vậy sau khi user verify, lần refresh kế tiếp sẽ có `email_verified=true` [SL; mapper email đọc thuộc tính user lúc map]. `validateToken` không kiểm required action đang chờ, nên refresh vẫn được dù user vừa bị gắn `VERIFY_EMAIL` [SL từ code].
- **Liên quan Revoke Refresh Token:** `validateTokenReuse` đếm số lần dùng mỗi refresh token, quá `refreshTokenMaxReuse` thì trả `invalid_grant` "Maximum allowed refresh token reuse exceeded". Nguồn: `TokenManager.java`, tra 2026-11-13 [CT]. BFF phải serialize refresh theo từng session (ví dụ khóa hàng trong Postgres) [SL].

## 6. Keycloak back-channel logout và `sid`

- **`sid` trong access token và ID token:** `TokenManager` gọi `token.setSessionId(userSession.getId())` khi dựng access token. `generateIDToken` gọi `idToken.setSessionId(accessToken.getSessionId())`. Claim JSON tên là `sid` (`IDToken.SESSION_ID = "sid"`). Nguồn: `TokenManager.java`, [`core/.../representations/IDToken.java`@26.8.2](https://github.com/keycloak/keycloak/blob/26.8.2/core/src/main/java/org/keycloak/representations/IDToken.java), tra 2026-11-13 [CT]. Vậy BFF index session theo `sid` của ID token được. Khi bật "lightweight access token", `sid` có còn trong access token không thì chưa kiểm **[CXM]**; nên lấy `sid` từ ID token.
- **`sid` trong `logout_token`:** `DefaultTokenManager.initLogoutToken` đặt các claim:
  - `jti`, `iat`, `exp` = now + 2 phút;
  - `iss`, `aud` = clientId;
  - `events` có `http://schemas.openid.net/event/backchannel-logout`, và thêm `revoke_offline_access` nếu bật option tương ứng;
  - `sub` = user id;
  - `sid` = user session id, **chỉ khi** `isBackchannelLogoutSessionRequired()`.
  
  Header `typ` là `logout+jwt` (`TokenUtil.TOKEN_TYPE_JWT_LOGOUT_TOKEN`). Nguồn: [`services/.../jose/jws/DefaultTokenManager.java`@26.8.2](https://github.com/keycloak/keycloak/blob/26.8.2/services/src/main/java/org/keycloak/jose/jws/DefaultTokenManager.java), [`core/.../util/TokenUtil.java`@26.8.2](https://github.com/keycloak/keycloak/blob/26.8.2/core/src/main/java/org/keycloak/util/TokenUtil.java), tra 2026-11-13 [CT]. Token được POST dạng form field `logout_token` (`ResourceAdminManager.sendBackChannelLogoutRequestToClientUri`) [CT].
- **Cấu hình client:** *Backchannel logout URL* gửi logout token theo spec, và docs ghi option này "applicable just if `Front channel logout` option is OFF". *Backchannel logout session required* quyết định `logout_token` có kèm `sid` hay không. Nguồn: [`server_admin/topics/clients/oidc/con-basic-settings.adoc`@26.8.2](https://github.com/keycloak/keycloak/blob/26.8.2/docs/documentation/server_admin/topics/clients/oidc/con-basic-settings.adoc), tra 2026-11-13 [CT]. Hệ quả: phải tắt Front channel logout trên client BFF [SL].
- **Khi nào Keycloak gửi back-channel logout** (đường code `AuthenticationManager.backchannelLogout` → `OIDCLoginProtocol.backchannelLogout` → backchannel logout URL):
  - **Đổi hoặc reset mật khẩu có tích "Sign out from other devices"** (form field `logout-sessions`): **có**. `UpdatePassword` gọi `AuthenticatorUtil.logoutOtherSessions`, hàm này duyệt mọi user session khác session hiện tại và gọi `backchannelLogout` cho từng session. Biến thể cho action token (flow reset qua email) cũng làm vậy. Nguồn: [`requiredactions/UpdatePassword.java`@26.8.2](https://github.com/keycloak/keycloak/blob/26.8.2/services/src/main/java/org/keycloak/authentication/requiredactions/UpdatePassword.java), [`authentication/AuthenticatorUtil.java`@26.8.2](https://github.com/keycloak/keycloak/blob/26.8.2/services/src/main/java/org/keycloak/authentication/AuthenticatorUtil.java), tra 2026-11-13 [CT].
  - **Admin "Sign out" một user** (`POST /admin/realms/{realm}/users/{id}/logout`): **có**. Keycloak đặt `notBefore` cho user, rồi gọi `backchannelLogout` cho từng session của user. Nguồn: [`services/resources/admin/UserResource.java`@26.8.2](https://github.com/keycloak/keycloak/blob/26.8.2/services/src/main/java/org/keycloak/services/resources/admin/UserResource.java) [CT].
  - **Admin xóa một session** (`DELETE /admin/realms/{realm}/sessions/{id}`): **có**, gọi `backchannelLogout`. Nguồn: [`RealmAdminResource.java`@26.8.2](https://github.com/keycloak/keycloak/blob/26.8.2/services/src/main/java/org/keycloak/services/resources/admin/RealmAdminResource.java) [CT].
  - **Admin "Sign out all active sessions" cả realm** (`POST /admin/realms/{realm}/logout-all`): **không gửi theo chuẩn OIDC**. Code gọi `session.sessions().removeUserSessions(realm)` rồi `ResourceAdminManager.logoutAll`. Hàm này đặt `notBefore` của realm và chỉ POST `LogoutAction` (định dạng riêng của Keycloak, endpoint `k_logout`) tới **Admin URL** của client. Docs cũng ghi Keycloak chỉ báo qua "Keycloak OIDC client adapter", và lệnh này "does not revoke outstanding access tokens". Nguồn: `RealmAdminResource.java`, [`services/managers/ResourceAdminManager.java`@26.8.2](https://github.com/keycloak/keycloak/blob/26.8.2/services/src/main/java/org/keycloak/services/managers/ResourceAdminManager.java), [`server_admin/topics/sessions/administering.adoc`@26.8.2](https://github.com/keycloak/keycloak/blob/26.8.2/docs/documentation/server_admin/topics/sessions/administering.adoc), tra 2026-11-13 [CT]. Với BFF: session cục bộ còn sống cho tới lần refresh kế tiếp. Lần đó Keycloak trả `invalid_grant` ("Session not active" hoặc "Stale token" do `notBefore`), và BFF phải coi đó là logout. Access token đã phát vẫn dùng được tối đa 5 phút [SL từ code].
